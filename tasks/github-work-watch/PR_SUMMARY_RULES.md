# 关注 PR 概要规则

## 输入与输出

从私仓 `MrZ20/data_repo` 的 `main` 分支读取 `data/github-work-watch/prs.json`。该文件是采集器的当前快照，每项包含 PR 地址、状态、代码更新时间和对应的 `head_sha`。每次执行还要读取自己上次写入的 `reports/github-work-watch/pr-summaries.md`。首次执行时报告不存在，按无已有概要处理。

将报告写入同一仓库 `main:reports/github-work-watch/pr-summaries.md`。报告只包含快照中当前存在的 PR，按 PR 号降序排列。同一 PR 用完整仓库名和编号识别。保留采集器的所有状态，包括 `draft`、`open`、`merged`、`closed`。状态或代码更新时间变化时同步报告中的字段。

每个条目按以下格式书写。已分析 commit 是用于形成当前概要的完整 head SHA，已分析目标分支是当时的 PR 目标分支，分析时间使用 UTC。这些字段是后续执行的检查点，不能根据 PR 当前状态猜测或提前更新。

````markdown
## [vllm-project/vllm-ascend#123](https://github.com/vllm-project/vllm-ascend/pull/123)

- 状态：open
- 代码更新时间：2026-11-19T09:00:00Z
- 已分析 commit：0123456789abcdef0123456789abcdef01234567
- 已分析目标分支：main
- 分析时间：2026-11-19T10:00:00Z

概要：为……增加……，使……可以……。
````

## 执行流程

1. 读取最新快照和上次报告，按仓库与 PR 号建立对应关系。快照的 `head_sha` 是本次需要检查的目标版本，不使用采集时间或分析时间充当版本。批量获取 PR 当前目标分支，便于发现目标分支变化。
2. 新 PR、没有已分析 commit 的旧报告条目，读取 PR 标题、描述和目标版本相对其目标分支的代码改动，形成概要。优先检查实际改动，描述只作为背景；描述和代码有差异时以代码为准。
3. 已分析 commit 和目标分支均未变化时，沿用概要和分析时间，更新状态及代码更新时间即可。commit 不同，读取两者之间的变化，并结合原概要判断 PR 的用途或用户可见行为是否发生变化。有变化就改写概要；无实质变化就保留原文字。两种情况都要在检查完成后将已分析 commit 和目标分支更新为已检查的值，并更新分析时间。
4. 检查旧 commit 是否为目标版本的祖先。旧 commit 不可访问、不是祖先、比较范围不完整或目标分支发生变化时，重新检查目标版本相对 PR 目标分支的完整改动，再决定概要。不能确认时保留原概要和原已分析 commit，留待下次重试。
5. 一次任务可以分批处理。已经完成的条目可以先保存，未完成的条目保留旧内容及旧检查点；没有旧概要的 PR 使用“已分析 commit：待分析”和“概要：待分析”，不能标成已完成。下一次从已分析 commit 与快照中的 `head_sha` 逐项比较，追上所有尚未处理的版本。连续多次推送时，可以直接检查上次已分析版本到最新快照版本之间的变化。

## 概要内容

用中文写 1 至 3 句话，说明 PR 在实现什么能力、调整什么行为或修复什么问题，以及必要的使用场景或影响范围。优先说明改动目的与结果。无需逐文件、逐函数解释实现，不推断尚未确认的效果。测试、文档或 CI 类 PR 说明它们覆盖或改变的工作。代码和描述不足以判断时，如实注明具体的不确定之处，不编造结论。

## 版本一致性与发布

读取代码时核对实际审查的 head SHA 与快照目标一致。GitHub PR 页面和普通 PR diff 可能在分析中继续变化；如果不能固定或确认版本，就保留旧检查点，下次重试。不要将新代码的概要标记为旧 SHA，也不要把旧代码的概要标记为新 SHA。

发布前重新读取最新快照和最新报告。对已分析的 PR，只有最新快照仍包含该 PR 且 `head_sha` 仍等于本次实际审查的版本，目标分支也未变化，才能写入新的概要和检查点。否则保留最新报告中已有内容，稍后按新快照处理。状态和代码更新时间采用发布前最新快照，报告中已经不在快照的 PR 移除。

以最新报告为基础合并本次完成的条目，并保留其他执行已经写入的较新结果。提交遇到冲突时重新读取、重新合并后重试，避免覆盖其他执行的更新。网络失败、读取失败或分析不完整时保留已存在的概要与检查点，不将失败视为成功。
